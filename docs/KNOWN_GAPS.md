# Known Gaps / Must-Fix-Before-Release

This file tracks deliberate, documented shortcuts taken during phased
development that are fine for a pre-release, in-progress codebase but MUST
be resolved before Phase 10 (Testing + CI/CD + Release) is considered done.
Each item exists so nothing gets silently forgotten.

| Item | Where | Why it's OK for now | Must be fixed before release because |
|---|---|---|---|
| **CurseForge support not implemented - no registered API key** | `CurseForgeConfig.kt` | Modrinth (the other major content source) is fully implemented and covers the same content types; CurseForge is additive, not a blocker for basic mod/shader/resource-pack functionality | Same pattern as the Azure AD client ID and JRE catalog: CurseForge's API requires a key registered at console.curseforge.com tied to this specific app. Once obtained, a `CurseForgeContentRepository` mirroring `ModrinthContentRepository`'s shape can be built and tested against real (or recorded) API responses - not attempted speculatively here without a key to verify against. |
| **Forge/NeoForge have NO installer-execution logic (`ForgeInstallerRunner.isImplemented() == false`)** | `ForgeInstallerRunner.kt` | Real version listing (`ForgeVersionRepository`) is complete and tested; only the actual jar-patching install step is missing, and it's explicitly marked rather than faked | Forge/NeoForge distribute versions as installer jars that patch the vanilla client jar's bytecode - fundamentally different from Fabric/Quilt (which only add libraries). This must either run the real installer jar's own logic or faithfully reimplement its `install_profile.json` processor steps; a "simplified" guess would produce installs that look complete but crash at runtime, which is worse than no support |
| **`MicrosoftAuthConfig.default.clientId` is blank - no registered Azure AD app** | `MicrosoftAuthConfig.kt` | The entire OAuth chain (device code -> Xbox Live -> XSTS -> Minecraft Services -> profile/ownership check) is real, complete, and tested against fakes; only the app registration itself is missing | This is a release blocker, not a coding task: whoever owns/distributes FrostByte must register a real Azure AD app at portal.azure.com with `XboxLive.signin` + `offline_access` permissions and put the resulting client ID here. `AuthRepository.signIn()` already checks this and fails immediately and honestly (`"not yet registered with Microsoft"`) rather than sending a doomed request. |
| **`HomeViewModel` does not yet call `LaunchPreparer`/`LauncherEngine`** | `HomeViewModel.kt` | Auth (Phase 5) now exists and is checked first; the remaining gap is a self-contained wiring step, not new subsystem work | Once wired, a real launch attempt will still correctly fail at whichever real blocker comes next (missing JRE catalog entry, missing downloaded libraries) - see the JRE entry below. The PLAY button currently reports this honestly rather than pretending. |
| **`JavaRuntimeCatalog` has no real, verified JRE download URLs** | `JavaRuntimeCatalog.kt` | The model/pipeline (download → extract → mark executable → verify by running `java -version`) is real and correct; only the actual URLs are placeholders | This is a hard release blocker, not a nice-to-have: without a real, Android/Bionic-compatible JRE build (verified to actually execute on-device), Minecraft cannot launch at all. Mojang's own JRE distribution does NOT work on Android (glibc vs Bionic - see the long comment in `JavaRuntimeManager.kt`) and must never be substituted in here as a shortcut. |
| **LWJGL / rendering has no Android compatibility layer at all** | Not yet started | Out of scope for Phase 4, which only covers "can we execute a java binary" | Even with a working JRE, Minecraft's LWJGL (window/OpenGL/audio) needs an Android-native build and a windowing/GL translation shim (the same category of problem PojavLauncher solves). This is arguably the single largest remaining piece of engineering in the entire project and needs to be scoped as its own phase, not assumed to "just work" once Java runs. |
| `fallbackToDestructiveMigration()` | `FrostByteDatabase.kt` | No public release exists yet, so there's no installed base with real data to lose | Real users upgrading between versions would silently lose all profiles/settings |
| Manual service locator instead of Hilt | `FrostByteContainer.kt` | Dependency graph is still small (≤10 repositories/services) | Revisit once the dependency graph gets unwieldy |
| `AuthRepository`'s device-code polling loop uses `System.currentTimeMillis()`, not an injectable clock | `AuthRepository.kt` | The `delay()` calls between polls correctly respect virtual test time via the injected dispatcher; only the expiry boundary check uses real time | Fine for now since it's a simple boundary condition, not complex logic, but a thorough test of "device code expired mid-poll" would need an injectable clock |

When you resolve an item, delete its row and note the resolution in
`CHANGELOG.md` instead.
